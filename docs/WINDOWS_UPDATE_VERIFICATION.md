# 更新流程驗收 — 逐步步驟（1.0.1 → 1.0.3）

> 本輪版本定義在 `update-test-round.json`（`from` / `target`），腳本一律從那裡讀。
> 要換測其他版本只需改那個檔，不必動任何腳本。

> **為什麼是 1.0.1 → 1.0.3，不是 1.0.0 → 1.0.1。**
> 上一輪在 VM 上實測，1.0.0 → 1.0.1 的更新**失敗**：檔案裝好了、`current.json` 也改了，
> 但服務從未換版，畫面卻顯示「更新已完成」（`BT-REL-001`）。
> 根因是新版的 service-control 把仍在服務的舊版判為陌生行程而拒絕停止它。
> **修正必須在「新版」裡** —— 它正是要去停舊服務的那一方。
> 所以 1.0.1 沒有修正、1.0.3 有，**1.0.1 → 1.0.3 是第一條可能走通的更新路徑**。

## 這一輪要證明什麼

| # | 要證明的事 |
| --- | --- |
| 1 | 1.0.1 的安裝能發現 1.0.3 |
| 2 | 使用者確認後才下載安裝 |
| 3 | **更新後服務真的在跑 1.0.3**（`BT-REL-001` 的修正） |
| 4 | 資料完整保留 |
| 5 | 更新橫幅出現在每一頁 |
| 6 | rollback 可用 |

## 前置：先讀這一段

**這份文件不需要你輸入或貼上任何指令。**

在 VM 裡到 `Z:\` 資料夾，**雙擊 `RUN-UPDATE-TEST.cmd`**，會跳出一個選單，
每一步只要按一個數字再按 Enter。本文各步驟會標明要按哪一個。

> 如果 Windows 跳出「開啟檔案 - 安全性警告」（因為是網路磁碟機上的檔案），按「執行」。
> 若選單文字是亂碼，先回報給我，不要硬跑。

先前的做法是叫人從 Markdown 複製一段多行的 PEM 公鑰貼進主控台 ——
**主控台不接受多行輸入**，所以那一步根本跑不起來。那是文件的錯，不是操作的錯。

本機帳號登入要打 `.\AcceptanceUser`。

> ⚠ **已知產品問題**：程式的簽章公鑰來自 `UPDATE_PUBLIC_KEY` 環境變數，預設是空的；
> 沒有公鑰時會直接丟 `BT-UPD-003`。公鑰是公開資訊，本來就該內建在產品裡 ——
> 現在的設計等於一般使用者永遠無法驗證更新。已記為 `BT-UPD-002`（P0），發佈前要處理。
> **本次測試用環境變數繞過，所以這一輪的通過不等於「出貨產品能驗簽」。**

## 步驟 1：還原 S1，然後裝上 1.0.1

VirtualBox → 快照 → 選 **`S1-with-chrome`** → 還原，登入 `.\AcceptanceUser`。

還原後是 1.0.0。**要先把它升到 1.0.1**，因為這一輪測的是 1.0.1 → 1.0.3。

在檔案總管開 `Z:\`，**雙擊 `BeybladeTracker-1.0.1-Setup.exe`**，全程使用預設值裝完。
（雜湊已在主機端比對過 GitHub 上 v1.0.1 的 manifest，相符。）

> 不要用上一輪那台已經跑過失敗更新的機器 —— 它的 `current.json` 是 1.0.1
> 而實際在跑 1.0.0，那個狀態不是任何真實使用者會有的。

---

## 步驟 2：跑前置設定腳本

在選單按 **`1`**。這支腳本會：確認目前版本是 1.0.1 → 檢查公鑰檔（並確認不含私鑰）→ 寫入兩個環境變數 →
**讀回來驗證**（特別是公鑰的換行有沒有掉）。

畫面出現 `=== 前置設定完成 ===` 才往下走。若有 `>>>` 開頭的行，先解決它 ——
帶著錯誤往下走只會得到 `BT-UPD-003`。

---

## 步驟 3：重啟服務讓它讀到新設定

環境變數只對**新啟動的行程**生效，所以服務一定要重開：

1. 開始功能表 →「**停止背景追蹤**」
2. 開始功能表 →「**Beyblade Tracker**」（會重新啟動服務並開管理頁）

等服務就緒（VM 上約 30～60 秒）。

> 這一步漏掉，整輪都白做，而且症狀是設定頁顯示「正式更新來源尚未設定」。

---

## 步驟 4 ⭐ 檢查更新橫幅出現在每一頁

**這一輪終於測得到這一項。** 上一輪要求在 1.0.0 上找橫幅，但全站橫幅
（`availableUpdateBanner`）是 **1.0.1 才引入**的（commit `aed1a69`）—— 在 1.0.0 上它按定義
不會出現，那份步驟是錯的。現在服務跑 1.0.1，橫幅應該真的在。

管理頁開啟後，**先不要去設定頁**。若橫幅沒立刻出現，到設定頁按一次「檢查更新」，
然後**回到總覽頁**再看。

| 位置 | 應該看到 |
| --- | --- |
| 總覽、商品、來源管理…**任何一頁** | 「**有新版本 1.0.3 可用。**」＋「前往設定查看」連結 |

也順便切一次英文，橫幅應變成 `Version 1.0.3 is available.` ＋ `Open Settings`。

> 這是「使用者收得到更新通知」的核心 —— 先前只有設定頁看得到，
> 使用者不主動去點就永遠不知道有新版。

---

## 步驟 5：確認「使用者確認後才安裝」

到設定頁，版本更新區塊應顯示：

- 可更新至 **1.0.3**
- 發行者、檔案大小、發佈時間、發佈說明
- 按鈕：**安裝更新**、**稍後更新**

**先按「稍後更新」**，確認：

- 按鈕變成「改為現在更新」
- 回到任一頁，橫幅改為「**版本 1.0.3 已延後安裝，可隨時改為現在更新。**」
  （較安靜的措辭，但入口還在）

> 這一步證明「檢查不會自動下載，只有使用者確認後才安裝」。

---

## 步驟 6 ⭐ 執行更新

**先記錄更新前的狀態**：

在選單按 **`2`**（記錄「更新前」）。

然後回設定頁按「**改為現在更新**」→「**安裝更新**」，確認提示後觀察：

| 階段 | 畫面應顯示 |
| --- | --- |
| 檢查 | 正在確認更新資訊與已簽署 manifest… |
| 下載 | 正在下載與驗證：N% |
| 安裝 | 正在安裝更新… |
| 完成 | 更新已完成，正在重新啟動服務並執行健康檢查。 |

服務會自行重啟。

---

## 步驟 7：確認更新結果

等服務重新就緒後：

在選單按 **`3`**（記錄「更新後」）。

兩段會寫在同一個 `update-test-counts.txt` 裡，直接上下對照。

| 檢查 | 預期 |
| --- | --- |
| `current.json` 版本 | `1.0.3` |
| `/health` 回報版本 | `1.0.3` —— **必須和上面一樣** |
| **資料筆數** | **與「更新前」那段完全相同**（更新不得動到使用者資料） |
| 更新橫幅 | **消失**（已經是最新） |
| 設定頁 | 顯示「目前已是最新版本。」 |

> ⚠ **兩個版本不一樣就停下來，按選單的 `6` 跑診斷。**
> `/health` 的版本讀自執行中的程式碼，所以「`current.json` 是新版、`/health` 是舊版」
> 代表**檔案換好了，但服務還在跑舊版**。畫面會說更新成功，實際上沒有。
> 這已記為 `BT-REL-001`。

順便確認 1.0.3 的改動確實生效：來源卡片切英文排版正常、錯誤訊息三語等。

---

## 步驟 7b：橫幅應該消失

更新成功後，1.0.3 已是最新，**任何一頁都不該再有更新橫幅**，設定頁顯示「目前已是最新版本。」

橫幅在步驟 4 已經驗過會出現；這一步驗它會**正確收起來** —— 一個永遠不消失的通知
和一個從不出現的通知一樣糟。

---

## 步驟 8：測 rollback

**設定頁不會有「回滾更新」按鈕 —— 這是正確的。** 那個按鈕只在**更新後健康檢查失敗**時
才出現（`server.js:309`，條件是 `updateHealth.rollbackOffered`）。你的更新成功了，
所以它不該在。找不到它不是問題。

回滾請在選單按 **`4`**。

跑完再在選單按 **`5`**（記錄「回滾後」）。

| 檢查 | 預期 |
| --- | --- |
| 版本 | 回到 `1.0.1` |
| 服務 | 能正常啟動 |
| **資料筆數** | **仍與「更新前」相同** |

> rollback 會用更新前自動建立的備份還原資料庫，所以筆數應與更新前一致。

## 如果失敗了

| 症狀 | 可能原因 |
| --- | --- |
| `BT-UPD-003` 更新無法驗證 | 公鑰沒設定或換行遺失 —— 重按選單的 `1`，看它的驗證段 |
| `BT-UPD-002` 無法取得更新資訊 | VM 沒有網路，或 manifest 網址打錯 |
| `BT-UPD-004` 更新檔案不符 | SHA-256 對不上；把畫面截圖給我，這代表產物或 manifest 有問題 |
| 設定頁顯示「正式更新來源尚未設定」 | **服務沒重啟**（步驟 3），或變數設在錯的範圍 |
| 腳本說 `/health 無回應` | 服務還在啟動；等 30 秒再按一次 |
| `current.json` 與 `/health` 版本不同 | **舊行程還佔著 8787**，更新沒真的生效 —— 按選單 `6` 診斷（`BT-REL-001`） |
| 設定頁找不到「回滾更新」按鈕 | 正常。它只在更新後健康檢查失敗時出現，改用選單 `4` |

有任何代碼或看起來不對的地方就截圖，不要硬推下去。

## 附錄：BT-UPD-002 驗證（更新設定內建於產物）

> 這一段與上面的更新流程無關，是**單獨一輪**。要證明的是：
> **一般使用者什麼都不設，更新功能就能運作。**

先前每一輪更新驗收，都是靠手動設 `UPDATE_MANIFEST_URL` 與 `UPDATE_PUBLIC_KEY` 才通過的。
兩者在 1.0.3 以前都只來自環境變數且預設為空 —— 也就是說，那些通過的結論
**對真實使用者從來不成立**。1.0.4 把兩者內建進產物。

### 為什麼一定要先清環境變數

**環境變數的優先權高於產物內建值。** VM 上的 `AcceptanceUser` 仍留著前幾輪設的那兩個值，
不清掉的話，就算修正完全失效，畫面看起來也會一模一樣 —— 這一輪就證明不了任何事。

### 步驟

**選單按 `9`** —— 清除兩個環境變數並記錄當下狀態。

然後**開始功能表 →「停止背景追蹤」→「Beyblade Tracker」**（環境變數只對新行程生效）。

到設定頁看「版本更新」區塊，**應顯示「正式更新來源尚未設定」**。
這正是修正前一般使用者的處境 —— 也證明先前幾輪確實是靠環境變數才過的。

**選單按 `A`** —— 比對安裝器雜湊、再次確認環境變數是空的、安裝 1.0.4、等服務就緒。

最後到設定頁確認：

| 看到 | 意思 |
| --- | --- |
| 「**目前已是最新版本。**」 | ✔ 通過。1.0.4 是最新版，能說出這句話就代表它**成功抓到並驗過了線上 manifest** |
| 「正式更新來源尚未設定」 | ✘ 內建網址沒讀到 |
| `BT-UPD-003` | ✘ 內建公鑰沒讀到 |

把共用資料夾裡的 `update-test-shipped-config.txt` 整份給我。
